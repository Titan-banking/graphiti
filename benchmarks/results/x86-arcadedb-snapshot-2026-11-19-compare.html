ArcadeDB build a37542d9 vs build e710f472: the Graphiti benchmark

The same benchmark (compare_arcadedb_falkordb.py: Graphiti's own driver and search functions, 1024-dimension embeddings, 3 groups, 4 CPU / 5 GB, 512 MB page cache) against two ArcadeDB builds, one run per cell. Old: build a37542d9 (26.12.1-SNAPSHOT (build a37542d996748abe76c3acfabcb68d5e2a117246/1795002496224/main), image arcadedata/arcadedb@sha256:87bd5febce2e09469269accbdb876b9386a2ef0870c2b78cff27a2ec37bba1e9). New: the latest snapshot, build e710f472.

Cards in engine read the exact columns, which use no vector index and so differ only by the ArcadeDB build (and the host). Cards in engine + driver read the ANN columns: Graphiti's driver changed between the runs too (a vector index over the edges, group_id = :group_id for one group, group_id declared STRING), so a change there is not the engine's alone. A change under 1.25x is shown as unchanged: identical queries in different columns of one run differ by about that much, and by more for bulk writes at small N.

What these runs do not tell you

  • The new build (e710f472) was created at 21:56 on 2026-11-19, before #12559 (the wide-record read) merged at 22:05: it does not contain it, nor any of the open PRs from this session (#12572, #12573, #12574, #12581).
  • The node-similarity ANN column got slower (see the table at N=50,000). The cause is not established; the edge index now shares the 512 MB page cache with the node index, which is a hypothesis, not a measurement.
  • One run per cell. The 512 MB page cache is the compose file's; at 2 GB the same ANN hybrid search measured 190 ms, not 366 ms.
