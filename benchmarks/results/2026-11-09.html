Findings

Single-host, one run per cell; absolute numbers are indicative, the ratios are the result.

  • Writes favour FalkorDB. Bulk load is ~1.3-1.5k rows/s on FalkorDB against 350-670 on ArcadeDB, and a single EntityEdge.save() stays ~1-2 ms on FalkorDB while on ArcadeDB it grows with the number of edges (18 ms at N=10k, 100 ms at N=50k with a vector index; 658 ms in the exact column, which is unexplained). Node saves are 1-2 ms vs ~2 ms. Under 8 concurrent writers ArcadeDB reports MVCC page conflicts as transient errors: none needed a harness retry at N=1k/10k, but at N=50k 6-8 batches per load failed even after the neo4j driver's own 30 s retry and were retried by the harness (row counts are verified afterwards).
  • Fulltext favours ArcadeDB at N >= 1k (node 3.7-10 ms vs 10-18 ms; edge 5-17 ms vs 14-19 ms) once edge fulltext reads each hit's endpoints with startNode/endNode. The previous MATCH ...-[e {uuid: rel.uuid}]->... form was ~100 ms per hit at 20k edges (ArcadeDB scans the edges there).
  • Node similarity: with the HNSW index ArcadeDB matches FalkorDB's exact scan at N=50k (31 ms vs 32 ms; recall@10 1.000 unquantized, 0.986 scalar). Without it ArcadeDB's exact scan is 468 ms at 50k.
  • Edge similarity has no ANN procedure in ArcadeDB (exact on both): 2.7-3.2 s vs 19.9 s per query at N=50k, so full hybrid search (dominated by it) is 2.8 s vs 20.6 s.
  • Engine-fused search (/vector/{db}/hybrid, HTTP only) is within ~1 ms of Graphiti's Python RRF over the same two legs from N=10k up.
  • Memory: FalkorDB holds the data in RAM (1.1 GB at 50k); ArcadeDB's JVM stays at ~3-4.3 GiB regardless. Disk is ~3x larger on ArcadeDB (1.8-2.2 GB vs 0.6 GB at 50k).

Setup notes: the ArcadeDB image tag is mutable, so the build is recorded above; the server's start script appends -XX:MaxRAMPercentage=75 after JAVA_OPTS, so the 2.5 GB heap is set with ARCADEDB_OPTS_MEMORY (see docker-compose.arcadedb.yml). Two earlier full runs failed at N=10k, once with a container OOM kill and once with the server going unresponsive, both with a ~6 GB heap and min_score=0. The run that passed changed both the heap (2.5 GB) and min_score (0.6, the library default), so the cause was not isolated; the Docker VM (16 GB) was also shared with unrelated containers.

Anomalies and caveats:

  • Possible integrity signal. During concurrent loads the ArcadeDB server logged 7 RecordNotFoundException: Record #x:y not found errors (in one isolated N=10k run) and, in an earlier run, a GhostEdgeReporter "dangling edge-segment pointer ... partially rolled-back transaction" warning. Node and edge counts matched N / 2N afterwards in every cell, but the harness did not look for dangling edges, so this is unquantified. Graphiti's bulk path writes the same way (8 concurrent execute_write transactions).
  • Run-to-run variance. Columns that run identical queries differ: BFS at N=50k is 699 ms in the exact column and 232 ms in the ANN columns, with no vector index involved. Treat single-run ratios below about 2x as noise.

Why ArcadeDB writes are slower

These experiments ran after the table above on the same build (b8824ed, source checked out at that commit); the table was not re-run, so its single-edge save() rows predate fix 1.

  1. Single-edge save() growing with N was a Graphiti query problem, now fixed. The ArcadeDB save query matched endpoints with MATCH (n:Entity {uuid: $edge_data.source_uuid}). ArcadeDB plans a parameter's field there as NodeByLabelScan with a filter (PROFILE), 36.8 ms per MATCH at 20k nodes against 0.73 ms for a flat $su (NodeIndexSeek). The save now passes flat parameters; EntityEdge.save() at 20k nodes went from ~66 ms to ~16 ms and no longer grows with the node count. The engine's own test for this (NestedParameterInMatchTest) only asserts the pattern resolves, not that the index is used. A one-row UNWIND [$edge_data] rewrite was worse (33 ms; a fixed per-statement cost that only amortises over a batch).
  2. Concurrent writers reduce throughput. Bulk edge insert on one 30k-node database: 703 edges/s with 1 writer, 446 with 2, 190 with 8 (with a server "Edge list OUT head chunk ... not visible yet (concurrent commit in flight)" conflict). Every edge rewrites the edge-list head of both endpoint vertices, and ArcadeDB's optimistic page-level concurrency makes writers that touch the same pages retry. FalkorDB serialises writes, so it does not pay this. The benchmark's 8-writer load therefore measured conflict cost; one writer was ~3.7x faster than 8 in that test (703 vs 190 edges/s), and in the benchmark's own run ~1.7x faster than its 8-writer 540-590 edges/s.
  3. The 1024-float fact_embedding is the per-edge floor. With one writer, an edge insert costs ~1.0 ms with the embedding and ~0.25 ms without (4x), and stays flat from 0 to 60k edges even with the 512 MiB page cache full.
  4. Not the cause: the fulltext index on RELATES_TO, the range indexes, the bucket count (1 vs 16) and MERGE vs CREATE each changed per-edge cost by under 10%.

Still open: why the exact column's edge saves were 6x slower than the ANN columns at N=50k, and the 7 RecordNotFoundException / ghost-edge entries.

Setup

  • ArcadeDB: 26.12.1-SNAPSHOT (build b8824ed068399aef60f7e06fb80241014469322d/1794261716931/main), image arcadedata/arcadedb@sha256:d35c537984a0e4db233c2d80745d86877c0f81aaba9c56b01aac9d1c0016937c
  • FalkorDB image: falkordb/falkordb@sha256:bef8acb1d8ed9ff8d2ea251767e75c6c05cfa759f7c6bc7e1c122f27d0ea4d7f
  • container limits: ArcadeDB 5 GB / 4 CPU, FalkorDB 5 GB / 4 CPU (docker), one engine running at a time
  • ArcadeDB JAVA_OPTS: -Darcadedb.server.rootPassword=playwithdata -Darcadedb.server.plugins=Bolt:com.arcadedb.bolt.BoltProtocolPlugin -Darcadedb.server.defaultDatabases=graphiti[root] -Darcadedb.maxPageRAM=512 -XX:MaxDirectMemorySize=1g
  • ArcadeDB ARCADEDB_OPTS_MEMORY: -Xms512m -Xmx2560m
  • shared Docker VM: 16 GiB RAM / 16 CPUs, also running unrelated containers throughout
  • host: macOS-26.4.1-arm64-arm-64bit-Mach-O, Apple M4 Max
  • graphiti PR #1310 head (fetched): 15963f0616f29ea0bd5865033b47f1c22f1ff455
  • this branch: f24536615b2bddf138420e2910c7132f8ea16a77
  • python: 3.13.13
  • embeddings: 64 clusters (centroid + noise), queries are a stored vector + noise
  • FalkorDB TIMEOUT: raised from the 1000 ms default to 0 so slow exact scans are measured, not aborted
  • dim=1024, reads: 200 queries after 20 warmup (50 for exact full scans), write concurrency 8, batch 500, limit 10, min_score 0.6 (the library default) for similarity
  • latencies are p50 / p95 in ms; ANN recall is recall@10 against the exact scan of the same data
  • container memory is the peak docker stats reading: for ArcadeDB (a JVM) it mostly reflects heap and page-cache sizing, not data size. Disk is the database directory (ArcadeDB pre-sizes 16 bucket files per type) or, for FalkorDB, the growth of the RDB after SAVE.
