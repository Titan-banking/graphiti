Findings

Single-host, one run per cell; absolute numbers are indicative, the ratios are the result.

  • Writes favour FalkorDB. Bulk load is ~1.3-1.5k rows/s on FalkorDB against 350-670 on ArcadeDB, and a single EntityEdge.save() is 1.2-2.2 ms on FalkorDB against 1.8-8.3 ms on ArcadeDB (1.9 ms ANN / 3.9 ms exact at N=50k; re-measured with flat endpoint parameters, see below). Node saves are ~1-2 ms on FalkorDB and 1.7-8.5 ms on ArcadeDB (the slow cells, 7.1 and 8.5 ms at N=1k and 10k, are in the exact column, the first one measured after the JVM warm-up; the ANN columns are 1.7-3.5 ms). Under 8 concurrent writers ArcadeDB reports MVCC page conflicts as transient errors: none needed a harness retry at N=1k/10k, but at N=50k 6-8 batches per load failed even after the neo4j driver's own 30 s retry and were retried by the harness (row counts are verified afterwards).
  • Fulltext favours ArcadeDB at N >= 1k (node 3.7-10 ms vs 10-18 ms; edge 5-17 ms vs 14-19 ms) once edge fulltext reads each hit's endpoints with startNode/endNode. The previous MATCH ...-[e {uuid: rel.uuid}]->... form was ~100 ms per hit at 20k edges (ArcadeDB scans the edges there).
  • Node similarity: with the HNSW index ArcadeDB matches FalkorDB's exact scan at N=50k (31 ms vs 32 ms; recall@10 1.000 unquantized, 0.986 scalar). Without it ArcadeDB's exact scan is 468 ms at 50k.
  • Edge similarity has no ANN procedure in ArcadeDB (exact on both): 2.7-3.2 s vs 19.9 s per query at N=50k, so full hybrid search (dominated by it) is 2.8 s vs 20.6 s.
  • Engine-fused search (/vector/{db}/hybrid, HTTP only) is within ~1 ms of Graphiti's Python RRF over the same two legs from N=10k up.
  • Memory: FalkorDB holds the data in RAM (1.1 GB at 50k); ArcadeDB's JVM stays at ~3-4.3 GiB regardless. Disk is ~3x larger on ArcadeDB (1.8-2.2 GB vs 0.6 GB at 50k).

Setup notes: this server is the mutable 26.12.1-SNAPSHOT tag, so the build is recorded above (CI and the compose file use the immutable release 26.11.1, on which the live suites also pass); the server's start script appends -XX:MaxRAMPercentage=75 after JAVA_OPTS, so the 2.5 GB heap is set with ARCADEDB_OPTS_MEMORY (see docker-compose.arcadedb.yml). Two earlier full runs failed at N=10k, once with a container OOM kill and once with the server going unresponsive, both with a ~6 GB heap and min_score=0. The run that passed changed both the heap (2.5 GB) and min_score (0.6, the library default), so the cause was not isolated; the Docker VM (16 GB) was also shared with unrelated containers.

Anomalies and caveats:

  • Integrity signals (7 RecordNotFoundException entries in one N=10k run and an earlier GhostEdgeReporter warning): node and edge counts matched N / 2N in every cell; the later audited stress runs found no mismatch (see the concurrency section below).
  • Run-to-run variance. Columns that run identical queries differ: BFS at N=50k is 699 ms in the exact column and 232 ms in the ANN columns, with no vector index involved. Treat single-run ratios below about 2x as noise.

Why ArcadeDB writes are slower

These experiments ran after the table above on the same build (b8824ed, source checked out at that commit); the single-save rows were then re-measured on the same build with --metrics save (flat parameters, write gate off): edge save c=1 p50 at N=50k went from 100.6 to 1.9 ms (ANN), 104.7 to 1.9 (scalar) and 657.8 to 3.9 (exact); c=8 from 361/362/1640 ms to 7.4/7.1/13.3 ms. Every other leg is unchanged from the original run. Treat only the N=50k edge-save change as established: node saves (unchanged code) vary 1.7-8.5 ms between columns and the early columns ran on a JVM that was not fully warm, so the smaller deltas at N=1k and 10k (including the c=8 cells that look slower) are within that noise.

  1. The slow single-edge save() was a nested-parameter MATCH that ArcadeDB plans as a scan (an engine bug, worked around in Graphiti). The save matched endpoints with MATCH (n:Entity {uuid: $edge_data.source_uuid}). PROFILE shows NodeByLabelScan with a filter for it and NodeIndexSeek [index=entity_uuid] for a flat $su: 36.8 ms vs 0.73 ms per MATCH at 20k nodes (a scan, so it grows with the node count). Cause in the engine at b8824ed: AnchorSelector.extractEqualityPredicatesFromExpression (optimizer/AnchorSelector.java:658-673) only accepts a literal or a plain $param on the other side of the equality, and NodeIndexSeek.resolveValue (operators/NodeIndexSeek.java:263) only resolves a plain ParameterExpression, so a $param.field is never used as a seek key. NestedParameterInMatchTest (issue #4909) only asserts the pattern returns a row. Graphiti now passes flat parameters: EntityEdge.save() at 20k nodes went from ~66 ms to ~16 ms (measured at that one size only). A one-row UNWIND [$edge_data] rewrite was worse (33 ms; a fixed per-statement cost that only amortises over a batch).
  2. Concurrent writers reduce throughput. Bulk edge insert on one 30k-node database: 703 edges/s with 1 writer, 446 with 2, 190 with 8 (with a server "Edge list OUT head chunk ... not visible yet (concurrent commit in flight)" conflict). Every edge rewrites the edge-list head of both endpoint vertices, and ArcadeDB's optimistic page-level concurrency makes writers that touch the same pages retry. FalkorDB serialises writes, so it does not pay this. The benchmark's 8-writer load therefore measured conflict cost; one writer was ~3.7x faster than 8 in that test (703 vs 190 edges/s), and in the benchmark's own run ~1.7x faster than its 8-writer 540-590 edges/s.
  3. The 1024-float fact_embedding is the per-edge floor. With one writer, an edge insert costs ~1.0 ms with the embedding and ~0.25 ms without (4x), and stays flat from 0 to 60k edges even with the 512 MiB page cache full.
  4. Not the cause of the per-edge floor: the fulltext index on RELATES_TO, the range indexes, the bucket count (1 vs 16) and MERGE vs CREATE each changed per-edge cost by under 10%. That ablation ran on a nearly empty RELATES_TO type (~6k edges), so it rules them out for the floor, not for growth with N.

The exact column's 6x slower edge saves were the same nested-parameter scan (it also has no vector index to keep up, so the scan competed with more work); with flat parameters it is 3.9 ms against 1.9 ms for ANN at N=50k.

Concurrency, integrity and upstream findings

In four interleaved gated/ungated pairs the gated run was faster every time (2,616 vs 1,352; 1,192 vs 758; 1,798 vs 1,364; 2,621 vs 1,503 edges/s). The runs below 1.5k coincide with slow single-writer runs in the same period (532-1,427 edges/s instead of ~2.5k), so the server was occasionally slow regardless of the setting. One writer reaches 2.4-2.7k edges/s when it is not. (Both columns above were measured through ArcadeDBDriver(write_concurrency=...); an earlier version of this table used a lock in the stress script instead of the driver's gate and is superseded.) A conflict costs the neo4j driver's 1 s retry back-off, which is why shortening it (0.02-0.05 s) only partly helped (1.05-1.97k edges/s) and not reliably, whereas admitting one writer at a time avoids the conflicts. Uniform endpoints (no hubs) scale just as badly, and transactions on strictly disjoint vertices (even interleaved ones, 20k to 2M vertices) never conflicted, so the conflicts are real shared-vertex collisions, not page false sharing. Each scenario ran 1-8 times; ranges above are those runs.

The gate costs throughput for many small independent writes: on a 10k-node / 20k-edge database, 8 concurrent callers of EntityNode.save / EntityEdge.save measured 194-211 and 222-286 saves/s with write_concurrency=1 against 589-1,137 and 462-1,198 ungated (3 interleaved runs each; with one caller the two are the same, 3-6 ms per save over Bolt). Pass write_concurrency=None when that pattern dominates and no two workers save the same edge at once.

A unique constraint on the relationship uuid (CREATE CONSTRAINT ... FOR ()-[e:RELATES_TO]-() REQUIRE e.uuid IS UNIQUE, idempotent with IF NOT EXISTS) is enforced (a second CREATE of the same uuid fails with ConstraintError) and, with the driver ungated, 150 distinct edges each saved by 4 concurrent workers stayed 150 stored edges. The losing savers got ConstraintError (328 of 600 calls through EntityEdge.save, 406 through add_nodes_and_edges_bulk) instead of matching the existing edge, and a plain retry made all 600 saves succeed with 150 edges stored. The constraint cannot be created over existing duplicate uuids. The driver does not create it, because that would turn silent duplicates into exceptions for every caller unless it also retried.

Integrity: in more than 40 audited scenarios (1-8 writers, 25 and 500 edges per batch) stored edge records, OUT-reachable and IN-reachable edges always equalled the committed count. The two GhostEdgeReporter warnings seen in ~35 minutes of mixed activity could not be reproduced in 35+ controlled reruns, including four with the stress run executing alongside unmanaged transactions that conflicted (~6,800 aborts) and were deliberately rolled back (~31,000), so no issue was filed for them. The 4 RecordNotFoundException: Cannot load OUT edge list chunk warnings logged earlier all came, per their stack traces, from a MERGE's read of an edge list (GraphEngine.getEdgeHeadChunk, the documented best-effort read side that answers an empty list when a head chunk is not yet visible and logs it at WARNING).

Separately, concurrent MERGE of the same relationship stores it more than once when its endpoints already have edges (no error): [ArcadeData/arcadedb#11482](https://github.com/ArcadeData/arcadedb/issues/11482), with a stdlib reproduction in benchmarks/arcadedb_concurrent_merge_repro.py. A unique constraint on the relationship property makes it exact. Through ArcadeDBDriver, 8 concurrent MERGEs of each of 600 relationships stored 3,875 edges ungated, 600 at write_concurrency=1 and 826 at 2 (4 clients x 2,000 relationships: 7,090, 2,000 and 3,045); through Graphiti's own write paths, 150 distinct edges each saved by 4 concurrent workers were stored as 357 (EntityEdge.save) and 425 (add_nodes_and_edges_bulk) edges ungated and as exactly 150 at write_concurrency=1. So the gate avoids it within one process only at 1; a live test keeps that true.

Upstream issues filed from this work: [#11480](https://github.com/ArcadeData/arcadedb/issues/11480) (nested $param.field is not an index seek key), [#11481](https://github.com/ArcadeData/arcadedb/issues/11481) (the relationship index is only used for single-type, unlabelled-endpoint WHERE lookups; the driver now uses that shape: get_by_uuid 44 -> 7 ms and delete 48 -> 16 ms at 20k edges), [#11482](https://github.com/ArcadeData/arcadedb/issues/11482) (concurrent relationship MERGE duplicates).
