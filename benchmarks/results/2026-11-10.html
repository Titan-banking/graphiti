Findings

Second full run, on ArcadeDB build ef10d046 (the 2026-11-09 run used b8824ed), same harness, data and settings. The ArcadeDB driver ran ungated (write_concurrency=None) as before, with the driver changes of the PR (index-friendly uuid lookups, flat edge-save parameters). One run per cell, so ratios under about 2x are noise.

  • Which cells ran where: FalkorDB (all sizes), ArcadeDB exact (all sizes) and ArcadeDB ANN at N=1,000 and N=10,000 ran on the first ArcadeDB container, arcadedb-graphiti. ArcadeDB ANN at N=50,000 and ArcadeDB ANN scalar (all sizes) ran on a second container, arcadedb-graphiti2, started after the first one hung. The Setup section above was recorded from the second container. Both were created with the same command: arcadedata/arcadedb:26.12.1-SNAPSHOT (the server reported build ef10d046 for both), 5 GB / 4 CPU, -Xms512m -Xmx2560m, -Darcadedb.maxPageRAM=512, -XX:MaxDirectMemorySize=1g. The first container's settings were not recorded in the file; they are known from the command that created it, and its container was not inspected afterwards. The two ran at different times (the first from about 14:00 to 17:00, the second after it), so the usual run-to-run variance applies across the split.
  • Run history: the first attempt hung on the ArcadeDB server (build ef10d046) during the ANN N=50,000 load, with eight writers loading edges ungated: the last server log entry is an HNSW graph build finishing at 21:34 UTC (16:34 local), and from then on it stopped answering HTTP and Bolt at 0% CPU, could not be killed (docker kill reported no exit event; the Docker VM and its disk were fine), and the client kept retrying until it was stopped at about 17:00 local. A SIGQUIT thread dump returned nothing, so there is no stack to show. The cause is undiagnosed (it could be the server or the Docker VM) and it did not repeat. The remaining ANN and ANN-scalar columns were measured on a second container of the same image, with the same limits, after the first finished columns. All twelve cells are complete.
  • The large gaps hold: at N=50,000, edge similarity 5.2 s vs FalkorDB 21.4 s (11-09: 3.2 s vs 19.9 s) and hybrid search 3.8 s vs 43.6 s (11-09: 2.8 s vs 20.6 s). ArcadeDB is 4x and 11x faster here, FalkorDB's own hybrid number doubled between runs.
  • Everything else is within noise or slightly worse: node similarity 45.6 vs 32.3 ms (11-09: 31.7 vs 31.5), node fulltext 15.7 vs 19.5 ms, edge fulltext 23.0 vs 19.7 ms, single saves 3-4 ms vs 1-2.5 ms, c=8 saves ~10 ms vs 4-9 ms. FalkorDB's BFS differs 3x between the two runs of the same engine (442 vs 150 ms), which is the run-to-run variance to keep in mind.
  • ArcadeDB's own numbers moved by about 1.0-1.7x between builds (similarity 31.7 to 45.6 ms, edge similarity 3.2 to 5.2 s, single edge save 1.9 to 3.5 ms), which is at the edge of this benchmark's noise; this run does not show a clear regression or improvement from the newer build.
  • Not in this run: the concurrency, integrity and write-gate findings (see the 2026-11-09 report), and the upstream issues, which #11486 is still open for.

Why bulk edge inserts were slower

The benchmark's bulk edge write is 313-592 edges/s on ArcadeDB against 1,421-1,443 on FalkorDB (50,000 nodes, 1024-dimension embeddings, 8 writers). Where the time goes, each step measured separately:

layermeasurementfinding
engine, bare statement500 random CREATE (a)-[:R]->(b) per transaction, HTTP, no properties62-71k edges/s with one writer
engine, Graphiti's statement on its real schemaMERGE ... SET e = edge, 8-dim embeddings, 136 indexes on RELATES_TO24 ms per 500 edges (20.7k edges/s); dropping every index only reaches 12.2k edges/s through the driver, so indexes are not the cost
engine, storing a 1024-float property per edgesame vector sent once, stored on 500 edges27.6 ms per 500 (18k edges/s)
client, Neo4j Python driver, 500 edges x 1024 floatsBolt round trip 354 ms, of which pure-Python PackStream encoding 203 ms and building a debug log line " ".join(map(repr, (query, parameters, extra))) about 118 ms (evaluated even with logging off); the server samples are 98-100% blocked in a socket readmost of the time is the client
client with neo4j-rust-ext and a constant-time-repr vectorsame batch21 ms per batch instead of 357 (17x)
through add_nodes_and_edges_bulk, single writer (drivers 6.1.0 and 6.4.1, matching extension)edges/s 1,163-1,176 -> 3,513-3,615; nodes/s 1,339-1,423 -> 7,785-7,889the driver change is in the PR; the extension is documented
concurrency, same engine8 writers on shared vertices vs one writer: 21k vs 62-71k edges/s; 8 writers on disjoint vertices 106-131kconflicting transactions: about 4 aborted attempts per commit take 83-89% of the commit-lock time. Filed as [ArcadeData/arcadedb#11498](https://github.com/ArcadeData/arcadedb/issues/11498) with a standard-library reproduction (benchmarks/arcadedb_concurrent_edge_insert_repro.py)
server retry settings, 8 writerstxRetries=50, txRetryDelayBase=25, txRetryDelay=800 vs defaults37.5k / 40.0k vs 17.8k / 17.9k edges/s, no 503s reach the client

So the single-writer difference with FalkorDB was the Python client, and the concurrent loss is conflict handling in the engine. The Nov 10 run also measured ArcadeDB exact bulk edges at 43 edges/s (171 retries) and ANN at 313, well below the 540 and 592 of Nov 9; that was the same run that later hung the server, so I treat it as unreliable rather than as a regression.

Setup

  • ArcadeDB: 26.12.1-SNAPSHOT (build ef10d046ae32370b0e9b6c39657149e969071cac/1794314192067/main), image arcadedata/arcadedb@sha256:da23ef2c18134e8691869cb7f764ea22a80618845a771fc9a827df5fe8dfe2e8
  • FalkorDB image: not recorded: the falkordb-bench container no longer existed when this file was written. The FalkorDB legs ran earlier in this run on the container created for the 2026-11-09 run (falkordb/falkordb@sha256:bef8acb1d8ed9ff8d2ea251767e75c6c05cfa759f7c6bc7e1c122f27d0ea4d7f), which is an inference, not something recorded.
  • ArcadeDB ARCADEDB_OPTS_MEMORY: -Xms512m -Xmx2560m
  • container limits: ArcadeDB 5 GB / 4 CPU, FalkorDB 5 GB / 4 CPU as in the 2026-11-09 run (not recorded for this file), one engine running at a time
  • ArcadeDB JAVA_OPTS: -Darcadedb.server.rootPassword=playwithdata -Darcadedb.server.plugins=Bolt:com.arcadedb.bolt.BoltProtocolPlugin -Darcadedb.server.defaultDatabases=graphiti[root] -Darcadedb.maxPageRAM=512 -XX:MaxDirectMemorySize=1g
  • shared Docker VM: 16 GiB RAM / 16 CPUs, also running unrelated containers throughout
  • host: macOS-26.4.1-arm64-arm-64bit-Mach-O, Apple M4 Max
  • graphiti PR #1310 head (fetched): 15963f0616f29ea0bd5865033b47f1c22f1ff455
  • this branch: bd6e2db16077360f20c3417d8dddb70630a9cbfa
  • python: 3.13.13
  • embeddings: 64 clusters (centroid + noise), queries are a stored vector + noise
  • FalkorDB TIMEOUT: raised from the 1000 ms default to 0 so slow exact scans are measured, not aborted
  • ArcadeDB driver write_concurrency: None (no gate): the columns measure the engine under 8 concurrent writers; the driver default of 1 writer per database is measured in arcadedb_concurrent_writes.py
  • dim=1024, reads: 200 queries after 20 warmup (50 for exact full scans), write concurrency 8, batch 500, limit 10, min_score 0.6 (the library default) for similarity
  • latencies are p50 / p95 in ms; ANN recall is recall@10 against the exact scan of the same data
  • container memory is the peak docker stats reading: for ArcadeDB (a JVM) it mostly reflects heap and page-cache sizing, not data size. Disk is the database directory (ArcadeDB pre-sizes 16 bucket files per type) or, for FalkorDB, the growth of the RDB after SAVE.
